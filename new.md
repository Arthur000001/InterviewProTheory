

## 1. Методы, указатели и композиция типов — P1

Сейчас: интерфейсы, typed nil, сравнение структур и передача по значению есть. Method set упоминается в ответе №142, но правил для `T`/`*T`, embedding и выбора receiver отдельными вопросами нет.

1. Чем отличаются `new(T)` и `make`, для каких типов они применимы и какие значения возвращают?

   **Ответ:** `new(T)` создаёт нулевое значение типа `T` и возвращает `*T`; место размещения определяет компилятор. `make` инициализирует только slice, map и channel и возвращает сам этот тип.

   ```go
   p := new(int)         // *int, значение 0
   s := make([]int, 0, 8)
   m := make(map[string]int)
   ch := make(chan int, 2)
   ```

   `new(map[string]int)` даёт указатель на nil-map: перед записью её ещё нужно инициализировать.

2. Как выбрать между value receiver и pointer receiver? Как выбор влияет на изменение состояния и копирование структуры?

   **Ответ:** Value receiver получает копию значения: подходит небольшим типам без изменяемого состояния. Pointer receiver позволяет менять исходный объект и избегать копирования большой структуры. Типы с mutex нельзя копировать после начала использования.

   Копирование структуры **поверхностное**: её slice/map могут продолжать ссылаться на общие данные. Сам по себе pointer receiver не обеспечивает потокобезопасность. Обычно методы одного типа используют согласованный стиль receiver.

3. Какие методы входят в method set типов `T` и `*T`? Почему вызов метода у переменной ещё не доказывает, что её тип реализует интерфейс?

   **Ответ:** Для обычного именованного типа `T` набор методов содержит методы с receiver `T`, а для `*T` — с receiver `T` и `*T`. У адресуемой переменной компилятор может автоматически взять адрес при вызове метода; при присваивании интерфейсу такого преобразования нет.

   ```go
   type Counter struct{ N int }
   func (c *Counter) Inc() { c.N++ }
   type Incrementer interface{ Inc() }

   var c Counter
   c.Inc()                    // (&c).Inc()
   var _ Incrementer = &c     // корректно
   // var _ Incrementer = c  // Counter не реализует интерфейс
   ```

4. Что такое embedding полей и интерфейсов? Как продвигаются методы и разрешаются конфликты имён?

   **Ответ:** Embedding — включение типа как поля без отдельного имени либо включение интерфейса в другой интерфейс. Поля и методы вложенного типа могут быть доступны через внешний объект. Это композиция: receiver продвинутого метода остаётся вложенным объектом.

   ```go
   type User struct{ Name string }
   type Admin struct{ User }
   // admin.Name эквивалентно admin.User.Name
   ```

   Более близкое объявление скрывает вложенное; одинаковые имена на одной глубине дают неоднозначность. У интерфейсов одноимённые методы должны иметь одинаковые сигнатуры. Встраивание `T` и `*T` по-разному влияет на method set.

5. Можно ли вызвать метод у nil-указателя и при каких действиях внутри метода возникнет panic?

   **Ответ:** Метод с pointer receiver можно вызвать у nil-указателя: nil передаётся как receiver. Panic возникает, если метод разыменует его, например прочитает поле, без проверки.

   ```go
   func (u *User) DisplayName() string {
       if u == nil { return "anonymous" }
       return u.Name
   }
   ```

   Вызов метода с value receiver через nil `*T` требует разыменования и паникует ещё до выполнения тела метода.

6. Чем method value отличается от method expression? Когда сохраняется receiver?

   **Ответ:** Method value `f := x.M` вычисляет и сохраняет receiver при создании `f`; затем вызывается как `f(args)`. Для value receiver сохраняется копия значения, для pointer receiver — указатель на тот же объект.

   Method expression `f := T.M` или `f := (*T).M` не привязывает объект: receiver становится первым явным аргументом — `f(x, args)`. Например, `(*Counter).Inc(&c)` вызывает метод для переданного счётчика.


Опора для формулировок: [спецификация Go](https://go.dev/ref/spec).


## 2. HTTP-сервер и HTTP-клиент на Go — P1

Сейчас: есть устройство HTTP, сравнение протоколов, graceful shutdown и общая рекомендация задавать таймауты. Реализация через `net/http` раскрыта недостаточно.

1. Как связаны `http.Handler`, `http.HandlerFunc` и `http.ServeMux`? Как построить цепочку middleware?

   **Ответ:** `http.Handler` задаёт метод `ServeHTTP(ResponseWriter, *Request)`. `HandlerFunc` адаптирует функцию этой сигнатуры к интерфейсу, а `ServeMux` выбирает обработчик по маршруту.

   ```go
   func withHeader(next http.Handler) http.Handler {
       return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
           w.Header().Set("X-Service", "users")
           next.ServeHTTP(w, r)
       })
   }
   ```

   Middleware принимает handler и возвращает handler. В `logging(auth(handler))` входящий запрос сначала проходит logging, затем auth; код после `next.ServeHTTP` выполняется в обратном порядке.

2. Когда фиксируются статус и заголовки ответа? Как влияет порядок вызовов `Header`, `WriteHeader` и `Write`?

   **Ответ:** Заголовки задают до окончательного `WriteHeader`. Первый `Write`, если статус ещё не отправлен, подразумевает `200 OK`. Последующие изменения обычных заголовков уже не изменят отправленный ответ; отдельно существуют информационные ответы 1xx и trailers.

   ```go
   w.Header().Set("Content-Type", "application/json")
   w.WriteHeader(http.StatusCreated)
   _, err := w.Write([]byte(`{"created":true}`))
   ```

   Поэтому ошибку желательно обнаружить до начала записи тела. Уже отправленный `200` нельзя заменить на `500`.

3. Какие данные handler могут одновременно использовать разные запросы? Можно ли продолжать использовать `ResponseWriter` после возврата из handler?

   **Ответ:** Один handler может обслуживать несколько запросов одновременно. Общими могут быть поля структуры handler, глобальные переменные, map, кеши и зависимости. Их изменяемое состояние защищают синхронизацией либо делают неизменяемым; локальные переменные запроса обычно независимы.

   `ResponseWriter` нельзя использовать после возврата из `ServeHTTP`. Фоновая горутина не должна продолжать писать ответ. Если работа вынесена в горутину, handler обязан дождаться её завершения и согласовать доступ.

4. За что отвечают `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` и `IdleTimeout`? Чем они отличаются от дедлайна в context?

   **Ответ:** `ReadHeaderTimeout` ограничивает чтение заголовков; `ReadTimeout` — чтение всего запроса, включая тело; `WriteTimeout` ограничивает запись ответа; `IdleTimeout` — ожидание следующего запроса в keep-alive соединении.

   Это ограничения сетевого обслуживания, **не команда остановить бизнес-логику**. Дедлайн context передаётся зависимостям и требует поддержки отмены кодом. Для потоковых ответов таймауты выбирают отдельно. [Документация Server](https://pkg.go.dev/net/http#Server).

5. Почему `http.Client` и `http.Transport` обычно переиспользуют? Как настроить пул и ограничения соединений?

   **Ответ:** Клиент и transport рассчитаны на повторное и конкурентное использование. Transport хранит соединения; создание нового на каждый запрос мешает reuse и увеличивает число TCP/TLS handshake.

   ```go
   tr := http.DefaultTransport.(*http.Transport).Clone()
   tr.MaxIdleConns = 100
   tr.MaxIdleConnsPerHost = 20
   tr.MaxConnsPerHost = 40
   client := &http.Client{Transport: tr, Timeout: 5 * time.Second}
   ```

   Лимиты примерные: их подбирают под нагрузку. Настройки задают до использования. `Client.Timeout` включает чтение тела ответа; контекст может задать более короткий бюджет.

6. Когда закрывать `resp.Body`, как чтение тела влияет на переиспользование соединения и как ограничить размер ответа?

   **Ответ:** После успешного `Do` вызывающий закрывает `resp.Body`, обычно через `defer`. Для reuse HTTP/1.x соединения тело обычно нужно дочитать до EOF и закрыть. Огромное или бесконечное тело нельзя дочитывать без лимита и таймаута.

   ```go
   defer resp.Body.Close()
   const limit = 1 << 20
   body, err := io.ReadAll(io.LimitReader(resp.Body, limit+1))
   if err != nil { return err }
   if len(body) > limit { return errors.New("response too large") }
   ```

   Дополнительный байт позволяет отличить допустимый размер от превышения; ограничение чтения может привести к отказу от reuse соединения.

7. Какие ошибки возвращает `Client.Do`? Как отдельно обрабатывать HTTP-статусы, ошибки сети и отмену контекста?

   **Ответ:** `Do` возвращает ошибку при проблеме выполнения запроса: сеть, TLS, перенаправления, отмена или таймаут. HTTP `404`/`500` сами по себе не означают ненулевой `err`: статус проверяют отдельно.

   Отмену и дедлайн различают через `errors.Is(err, context.Canceled)` и `errors.Is(err, context.DeadlineExceeded)`; свойства сетевой ошибки — через `errors.As`. Ошибка чтения тела может возникнуть уже после успешного `Do`. Ретраи зависят от причины и идемпотентности операции.

8. Что происходит с `r.Context()` при отключении клиента и завершении handler? Как передать его исходящему запросу?

   **Ответ:** Контекст входящего запроса отменяется при закрытии клиентского соединения, отмене HTTP/2-запроса или возврате handler. Его передают зависимостям, чтобы ненужная работа могла остановиться.

   ```go
   req, err := http.NewRequestWithContext(r.Context(), http.MethodGet, url, nil)
   if err != nil { /* вернуть ошибку запроса */ return }
   resp, err := client.Do(req)
   ```

   Отмена не убивает произвольную горутину: она должна проверять context или вызывать API с поддержкой отмены.


Опора: [пакет net/http](https://pkg.go.dev/net/http).


## 3. gRPC и Protobuf на практике — P2

Сейчас: сравнение gRPC/REST и передача дедлайна присутствуют. Реализация и развитие контракта не разобраны.

1. Как `.proto` превращается в Go-код клиента и сервера? Как организовать воспроизводимую генерацию?

   **Ответ:** В `.proto` описывают сообщения и сервис; `protoc` с `protoc-gen-go` генерирует типы сообщений, а с `protoc-gen-go-grpc` — клиентские и серверные API. `go_package` определяет Go import path.

   Версии компилятора, плагинов и proto-зависимостей фиксируют; команду генерации хранят в репозитории. В CI повторяют генерацию и проверяют отсутствие неожиданного diff. `go generate` лишь запускает указанные команды и не выполняется автоматически при `go build`.

2. Чем unary RPC отличается от server-streaming, client-streaming и bidirectional-streaming по жизненному циклу вызова?

   **Ответ:** Unary — один запрос и один ответ. Server streaming — один запрос, поток ответов. Client streaming — поток запросов и один итоговый ответ. Bidirectional streaming — два независимых потока внутри одного RPC.

   Внутри каждого направления порядок сообщений сохраняется. Закрытие клиентом отправки не означает прекращение чтения ответов: итоговый статус ещё нужно получить. Стрим живёт до штатного завершения, ошибки или отмены.

3. Для чего нужны interceptors и metadata? Как применять аутентификацию, логирование и tracing?

   **Ответ:** Interceptor — обёртка RPC для общей логики; для unary и streaming используются соответствующие варианты. Metadata передаёт пары ключ–значение: например, токен или идентификатор запроса.

   На сервере проверяют credentials, формируют доверенную identity в context, измеряют длительность и записывают статус. Права на конкретный объект проверяют в прикладной логике. Для tracing используют согласованную инструментацию, например OpenTelemetry; секреты из metadata не логируют.

4. Как преобразовывать доменные ошибки в gRPC status codes, не раскрывая внутренние детали?

   **Ответ:** На границе сервиса сопоставляют доменные ошибки со стабильными кодами: некорректный ввод → `InvalidArgument`, отсутствие сущности → `NotFound`, дубликат → `AlreadyExists`, отсутствие identity → `Unauthenticated`, запрет доступа → `PermissionDenied`.

   Неожиданную ошибку БД логируют с внутренними подробностями, клиенту возвращают `Internal` и безопасное сообщение. Отмену и дедлайн сохраняют как `Canceled`/`DeadlineExceeded`. Код описывает ситуацию для клиента, а не конкретный драйвер.

5. Как изменять Protobuf-схему совместимо? Почему важны номера полей, `reserved` и различие отсутствующего и нулевого значения?

   **Ответ:** Номер поля — его идентификатор в wire format; удалённые номера нельзя переиспользовать. Удалённые номера и имена помечают `reserved`. Обычно безопаснее добавить новое поле, чем менять смысл или тип старого.

   В proto3 обычное скалярное поле с implicit presence не различает отсутствие и нулевое значение; для присутствия применяют `optional`, message или `oneof`. Совместимость проверяют отдельно для бинарного формата, JSON и прикладной семантики. [Правила Protobuf](https://protobuf.dev/programming-guides/proto3/).

6. Как обрабатывать отмену и завершение стрима, медленного получателя и освобождение ресурсов?

   **Ответ:** На сервере отслеживают `stream.Context()`, ошибки `Send`/`Recv`; на клиенте задают context с разумным дедлайном. `io.EOF` при `Recv` означает штатное завершение соответствующего входящего потока, остальные ошибки нужно обработать.

   Flow control может задерживать отправку медленному получателю, поэтому промежуточные очереди ограничивают. Допустимы одна горутина отправки и одна чтения, но не несколько конкурентных `Send` одного стрима. При остановке отменяют контекст, дожидаются работников и закрывают ресурсы. [gRPC Go](https://grpc.io/docs/languages/go/basics/).


## 4. Безопасность API и аутентификация — P1/P2

Сейчас: раздел `architecture/security` пуст, однако карточка №369 уже покрывает SQL injection, случайные токены, пароли, path traversal и некоторые другие меры. Ниже — дополнение к ней.

1. Чем аутентификация отличается от авторизации? Где проверять право пользователя на конкретный объект, чтобы избежать доступа к чужим данным?

   **Ответ:** Аутентификация устанавливает, кто обращается; авторизация — что ему разрешено. Одного валидного токена недостаточно для доступа к `/orders/123`.

   Сервис проверяет владельца, tenant и роль для **каждой операции над объектом**, включая списки и изменение данных. Например, выборка `WHERE id = $1 AND tenant_id = $2` использует tenant из проверенной identity, а не из произвольного поля запроса. Проверка только на фронтенде не защищает API.

2. Чем серверная сессия отличается от JWT? Какие данные JWT нужно проверять помимо подписи?

   **Ответ:** При серверной сессии клиент хранит непрозрачный ID, а состояние и отзыв контролирует сервер. JWT содержит claims и проверяемую подпись; его можно валидировать без обращения к хранилищу сессий, но немедленный отзыв требует отдельного механизма.

   Проверяют разрешённый алгоритм и доверенный ключ, `iss`, `aud`, сроки `exp`/`nbf` и назначение токена. Декодирование не равно проверке. Подписанный JWT обычно **не зашифрован**: секретные данные в payload не помещают.

3. Как организовать срок жизни, обновление и отзыв токенов? Что делать при утечке refresh token?

   **Ответ:** Access token делают короткоживущим, refresh token хранят защищённо и ограничивают сроком действия. При обновлении refresh token ротируют, а повторное использование старого обнаруживают на сервере.

   При компрометации отзывают сессию или семейство refresh-токенов и требуют повторный вход. Уже выпущенный access JWT действует до истечения срока, если нет denylist, проверки версии сессии или introspection. В браузере cookie защищают `HttpOnly`, `Secure`, подходящим `SameSite` и мерами против CSRF.

4. Чем OAuth 2.0 отличается от OpenID Connect и какую задачу решает каждый?

   **Ответ:** OAuth 2.0 описывает делегированный доступ клиента к ресурсам через access token и scopes. Сам по себе он не стандартизует вход пользователя.

   OpenID Connect добавляет слой идентификации: ID token, стандартные claims и способы получения сведений о пользователе. ID token предназначен клиенту для проверки входа; API принимает access token своего назначения. Для типичного интерактивного входа используют Authorization Code с PKCE и проверками параметров протокола.

5. Что такое CORS и CSRF? Почему разрешённый origin не заменяет проверку прав доступа?

   **Ответ:** CORS определяет, каким web-origin браузер разрешит читать межсайтовый ответ. CSRF — выполнение нежелательной операции через браузер пользователя с автоматически приложенными credentials, например cookie.

   Защита от CSRF включает токен, проверки Origin и подходящий SameSite; изменяющие операции не делают через GET. CORS не аутентифицирует клиента, не запрещает обращения вне браузера и не заменяет авторизацию. Некоторые межсайтовые запросы могут отправляться даже без разрешения читать ответ.

6. Как возникает SSRF в сервисе, который загружает URL пользователя? Какие проверки нужны для адресов, перенаправлений и доступа к внутренней сети?

   **Ответ:** При SSRF злоумышленник заставляет backend запросить внутренний сервис, localhost или metadata endpoint через пользовательский URL. Предпочтительны разрешённые назначения и протоколы, а не произвольный доступ.

   Проверяют URL, все полученные IPv4/IPv6 адреса и каждый redirect; ограничивают порты, время, размер ответа и сетевой egress. Проверенный адрес должен совпадать с адресом фактического подключения, иначе возможна подмена через DNS. Одной проверки строки hostname недостаточно. [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

7. Что проверяет TLS-клиент и когда нужен mTLS? Как передавать и обновлять секреты, исключая их попадание в логи?

   **Ответ:** TLS-клиент проверяет цепочку сертификатов до доверенного центра, срок действия и имя сервера. Отключение проверки сертификата разрушает проверку подлинности соединения. При mTLS сервер дополнительно проверяет клиентский сертификат; прикладные права всё равно проверяются отдельно.

   Секреты получают из управляемого хранилища по минимальным правам, обновляют с контролируемой ротацией и исключают из URL, дампов конфигурации, логов и tracing. Логируют идентификатор версии секрета, а не его значение.


## 5. Kubernetes: ресурсы и управление приложением — P1

Сейчас: есть kubelet, etcd, кворум, finalizers и graceful shutdown. Основные объекты приложения и цикл управления ими отдельно не разобраны.

1. Что такое Pod и чем он отличается от контейнера? Какие ресурсы разделяют контейнеры одного Pod и как они обращаются друг к другу?

   **Ответ:** Pod — минимальная единица размещения Kubernetes: один или несколько связанных контейнеров на одной ноде. Они разделяют сетевое пространство, IP и порты, поэтому обращаются друг к другу через `localhost`.

   Общие данные передают через подключённые volumes; корневые файловые системы контейнеров остаются отдельными. Общее пространство процессов включается отдельно. Pod используют для тесно связанных компонентов, а независимые реплики приложения размещают в разных Pod. [Pods](https://kubernetes.io/docs/concepts/workloads/pods/).

2. Как связаны Deployment, ReplicaSet и Pod? Кто восстанавливает нужное число реплик после удаления Pod?

   **Ответ:** Deployment управляет ReplicaSet и обновлением шаблона приложения. ReplicaSet поддерживает нужное число Pod, соответствующих его selector. При удалении Pod именно контроллер ReplicaSet создаёт замену; новый Pod получает новый UID и может оказаться на другой ноде.

   Kubelet перезапускает контейнеры внутри назначенного ему Pod согласно политике, но не отвечает за восстановление количества реплик Deployment. Для остановки приложения меняют желаемое число реплик либо удаляют управляющий объект.

3. Что происходит после создания Deployment через Kubernetes API? За что отвечают API server, scheduler и контроллеры?

   **Ответ:** API server аутентифицирует и авторизует запрос, выполняет проверки/admission и сохраняет объект в etcd. Deployment-controller создаёт ReplicaSet, его контроллер — Pod. Scheduler выбирает подходящую ноду для ещё не назначенного Pod и фиксирует назначение.

   Kubelet на этой ноде через runtime запускает контейнеры, подключает необходимые ресурсы и сообщает статус. Компоненты согласуют состояние асинхронно: успешное создание Deployment ещё не означает готовность приложения.

4. Когда выбирать Deployment, StatefulSet или DaemonSet? Какие гарантии StatefulSet даёт относительно имён и хранилища, а какие задачи БД он не решает?

   **Ответ:** Deployment подходит взаимозаменяемым репликам stateless-приложения. StatefulSet даёт устойчивую идентичность реплик, упорядоченные операции согласно политике и отдельные PVC по шаблону. DaemonSet размещает Pod на каждой подходящей ноде, например агент логирования.

   StatefulSet не реализует репликацию БД, выбор лидера, backup и защиту от split brain. Эти задачи решает сама БД, оператор и эксплуатационные процедуры; устойчивое имя Pod не равно сохранности данных.

5. Чем Job отличается от CronJob? Как работают повторы, ограничение времени выполнения и `concurrencyPolicy`?

   **Ответ:** Job запускает работу до заданного успешного завершения; CronJob создаёт Job по расписанию. `backoffLimit` ограничивает повторы, `activeDeadlineSeconds` — время работы Job; `parallelism` и `completions` задают параллелизм и число успешных выполнений.

   У CronJob `concurrencyPolicy` задаёт `Allow`, `Forbid` или `Replace` для его собственных запусков. Возможны повторные и пропущенные запуски, поэтому побочные эффекты делают идемпотентными. Ограничение конкуренции одного CronJob не является глобальной блокировкой. [Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/).

6. Для чего нужны init containers и sidecar-контейнеры? Как их жизненный цикл связан с основным приложением?

   **Ответ:** Обычные init containers последовательно выполняют подготовку и должны успешно завершиться до запуска основных контейнеров. Sidecar работает рядом с приложением: прокси, агент или сборщик данных.

   Встроенный sidecar задают в `initContainers` с `restartPolicy: Always`: после его старта могут запускаться следующие контейнеры, а при завершении Pod он останавливается после основных. Такой sidecar не мешает завершению Job. Исторический sidecar в обычном `containers` не обладает всеми этими гарантиями. [Sidecar containers](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/).

7. Как работают labels, selectors и namespaces? Почему namespace сам по себе не обеспечивает сетевую изоляцию?

   **Ответ:** Labels — метки объектов, selectors — условия выбора по меткам. По ним Service находит endpoints, а контроллеры — управляемые ресурсы. Namespace разделяет имена и область действия многих объектов, прав и квот; ноды и некоторые другие ресурсы остаются кластерными.

   Namespace сам не запрещает сетевые соединения между Pod. Для ограничения трафика нужны NetworkPolicy и поддерживающая их сетевая реализация; для доступа к API — RBAC.

8. Чем желаемое состояние объекта отличается от наблюдаемого? Что такое reconciliation и почему ручное удаление управляемого Pod не останавливает Deployment?

   **Ответ:** `spec` описывает желаемое состояние, `status` — наблюдаемое состояние, которое публикуют компоненты системы. Reconciliation — повторяющийся цикл сравнения и действий для устранения расхождения.

   Если в Deployment требуется три реплики, удаление одного Pod временно оставляет две. Контроллер создаст недостающую. Менять нужно источник желаемого состояния; при GitOps прямую правку объекта может дополнительно отменить контроллер доставки.


Опора: [ресурсы рабочих нагрузок Kubernetes](https://kubernetes.io/docs/concepts/workloads/).

## 6. Kubernetes: сеть, конфигурация и хранилище — P1/P2

Сейчас: есть сравнение сетевых прокси, проблема `ndots:5` и общие вопросы о секретах. Не хватает устройства доступа к приложению и подключения его зависимостей. Вопросы 1–5 — P1, 6–8 — P2.

1. Зачем нужен Service и как он выбирает Pod через selector и EndpointSlice? Чем отличаются `port`, `targetPort` и `nodePort`?

   **Ответ:** Service предоставляет стабильную точку обращения к меняющемуся набору Pod. Для Service с selector контроллер формирует EndpointSlice с адресами и состоянием endpoints; сетевой dataplane направляет трафик к подходящим адресам.

   `port` — порт Service, `targetPort` — порт приложения в Pod, `nodePort` — выделенный порт на нодах для соответствующего типа Service. `targetPort` может ссылаться на именованный порт контейнера. Selector не проверяет, действительно ли приложение слушает нужный порт. [Service](https://kubernetes.io/docs/concepts/services-networking/service/).

2. Когда использовать ClusterIP, NodePort, LoadBalancer или headless Service? Как сервис обнаруживается через DNS?

   **Ответ:** ClusterIP даёт виртуальный адрес внутри кластера. NodePort публикует сервис через порт ноды. LoadBalancer запрашивает внешнюю балансировку у доступной реализации. Headless (`clusterIP: None`) не выделяет виртуальный IP и позволяет обнаруживать отдельные endpoints.

   DNS-имя обычно имеет вид `service.namespace.svc.<cluster-domain>`: для обычного Service оно указывает на ClusterIP, для headless — на адреса endpoints по правилам публикации. Внешний балансировщик требует поддержки окружения, а не возникает только от записи `type`. [Service](https://kubernetes.io/docs/concepts/services-networking/service/).

3. Чем Service отличается от Ingress и Gateway API? Зачем нужны соответствующие контроллеры и где завершается TLS?

   **Ответ:** Service в основном предоставляет доступ к набору endpoints на транспортном уровне. Ingress описывает HTTP(S)-маршрутизацию по host/path. Gateway API разделяет инфраструктурный gateway и маршруты, поддерживая более выразимые политики и роли.

   Для реализации правил нужен контроллер: сами API-объекты трафик не проксируют. TLS может завершаться на внешнем балансировщике/gateway либо проходить до backend — это определяется настройкой и поддержкой реализации. После TLS termination соединение к приложению настраивают отдельно.

4. Чем ConfigMap отличается от Secret? Как передавать их через переменные окружения и файлы, и когда приложение увидит обновление?

   **Ответ:** ConfigMap хранит несекретную конфигурацию, Secret — чувствительные значения. Base64 в Secret — кодирование, не шифрование: нужны RBAC и настройка защиты хранения.

   Переменные окружения получают значения при запуске контейнера; для обновления нужен его перезапуск. Проецируемые файлы обычно обновляются с задержкой, но приложение должно перечитать их; монтирование через `subPath` автоматическое обновление не получает. Ротация файла сама по себе не обновляет уже созданный клиент БД. [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).

5. Как проверить путь запроса от внешнего клиента до Go-приложения, если Pod работает, но Service не отвечает? Как влияют неверный selector, порт и привязка приложения к `127.0.0.1`?

   **Ответ:** Проверяют цепочку: внешний балансировщик → маршрут Ingress/Gateway → Service → EndpointSlice → IP и порт Pod → приложение. Сначала проверяют наличие готовых endpoints, selector и `targetPort`, затем доступность Pod из другого Pod и сетевые политики.

   ```bash
   kubectl get svc,endpointslices,pods -n app
   kubectl describe svc api -n app
   kubectl logs deployment/api -n app
   ```

   Go-сервер на `127.0.0.1:8080` принимает соединения только внутри сетевого пространства Pod. Для обращения через Pod IP обычно слушают `:8080`. Running не означает Ready.

6. Как работают NetworkPolicy для входящего и исходящего трафика? Как разрешить только обращения к БД и DNS и от чего зависит применение политики?

   **Ответ:** NetworkPolicy выбирает Pod и разрешает ingress/egress по источникам, назначениям и портам. Если Pod изолирован для направления, разрешения нескольких политик складываются; для соединения должны быть разрешены исходящий трафик источника и входящий трафик получателя, если они изолированы.

   Обычно начинают с default deny и разрешают БД по нужным selectors/порту, а DNS — к реальному resolver по UDP/TCP 53. Политики исполняет поддерживающая их сетевая реализация. Стандартная NetworkPolicy не фильтрует произвольные URL или HTTP-пути. [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

7. Как связаны PV, PVC, StorageClass и CSI? Чем постоянное хранилище отличается от `emptyDir` и что происходит с данными после удаления Pod или PVC?

   **Ответ:** PVC — запрос приложения на хранилище, PV — ресурс тома, StorageClass — класс и параметры выделения, CSI — интерфейс драйвера для работы с системой хранения. PVC связывается с PV, часто созданным динамически.

   `emptyDir` существует в рамках Pod и переживает перезапуск контейнера, но удаляется вместе с Pod. Постоянный том может пережить Pod; удаление PVC запускает дальнейший жизненный цикл согласно reclaim policy (`Retain`/`Delete`) и защите используемых ресурсов. Для StatefulSet учитывают также политику удержания PVC. [Persistent Volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/).

8. Зачем Pod нужен ServiceAccount? Чем Role/RoleBinding отличаются от ClusterRole/ClusterRoleBinding и как ограничить доступ приложения к Kubernetes API?

   **Ответ:** ServiceAccount задаёт identity workload при обращении к Kubernetes API. Role описывает разрешения в namespace; ClusterRole может описывать кластерные разрешения и переиспользоваться в namespace. RoleBinding выдаёт права в своём namespace, ClusterRoleBinding — на уровне кластера.

   Приложению выделяют отдельный ServiceAccount и только нужные verbs/resources; избегают wildcard и `cluster-admin`. Если доступ к API не нужен, отключают автоматическое монтирование токена. Наличие ServiceAccount не даёт прав на бизнес-объекты приложения.



## 8. Базы данных: моделирование и SQL — P1

1. Что такое функциональная зависимость и нормальные формы 1NF, 2NF и 3NF? Какие аномалии изменения данных устраняет нормализация?

   **Ответ:** Функциональная зависимость `X → Y` означает: одинаковое значение X однозначно определяет Y. 1NF исключает повторяющиеся группы и требует значений в рамках выбранных атомарных доменов. 2NF дополнительно исключает зависимость неключевых атрибутов от части составного кандидатного ключа. 3NF исключает нежелательные транзитивные зависимости; формально для нетривиальной зависимости X → A нужен суперключ X либо ключевой атрибут A.

   Например, имя отдела хранят в `departments`, а сотруднику задают `department_id`. Это устраняет необходимость менять имя отдела во множестве строк и уменьшает аномалии вставки, обновления и удаления.

2. Как моделировать связи один-к-одному, один-ко-многим и многие-ко-многим? Как выбрать естественный или суррогатный первичный ключ?

   **Ответ:** Один-к-одному обычно моделируют внешним ключом с UNIQUE; один-ко-многим — FK в таблице «многие»; многие-ко-многим — таблицей связей с двумя FK и уникальностью их пары. `NOT NULL` отдельно задаёт обязательность ссылки.

   Естественный ключ имеет бизнес-смысл, например неизменяемый код; суррогатный — технический ID. Если бизнес-идентификатор может измениться или слишком велик, удобен суррогатный ключ, но уникальность бизнес-значения всё равно обеспечивают ограничением. Выбор UUID или числа зависит от генерации, распределённости и индексов.

3. Чем `UNION` отличается от `UNION ALL`? Как удаление дублей влияет на результат и стоимость запроса?

   **Ответ:** `UNION ALL` объединяет результаты, сохраняя повторяющиеся строки. `UNION` удаляет дубли по всем столбцам результата, что обычно требует дополнительного хеширования или сортировки.

   Число столбцов должно совпадать, а типы — быть совместимыми. Если повторы допустимы или исключены логикой, `UNION ALL` избегает ненужной работы. Порядок строк без итогового `ORDER BY` не гарантируется ни в одном варианте.

4. Как работают оконные функции `ROW_NUMBER`, `RANK`, `LAG` и агрегаты с `OVER`? Как влияют `PARTITION BY`, `ORDER BY` и рамка окна?

   **Ответ:** Оконная функция вычисляет значение по связанным строкам, сохраняя отдельные строки результата. `PARTITION BY` делит их на группы, `ORDER BY` задаёт порядок внутри окна. `ROW_NUMBER` нумерует строки; `RANK` даёт одинаковый ранг совпадениям с пропусками; `LAG` обращается к предыдущей строке.

   Для оконного агрегата рамка определяет участвующие строки. Например, `SUM(amount) OVER (PARTITION BY account_id ORDER BY created_at, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` считает накопительную сумму. Рамку лучше задавать явно: рамка по умолчанию с ORDER BY учитывает строки с равными ключами. [Оконные функции](https://www.postgresql.org/docs/current/tutorial-window.html).

5. Как получить последнюю запись и top-N записей для каждой группы? Как обеспечить определённый результат при совпадающих значениях сортировки?

   **Ответ:** Строки ранжируют внутри каждой группы и фильтруют во внешнем запросе. Последняя запись — `rn = 1`, top-N — `rn <= N`.

   ```sql
   SELECT *
   FROM (
       SELECT e.*,
              ROW_NUMBER() OVER (
                  PARTITION BY user_id
                  ORDER BY created_at DESC, id DESC
              ) AS rn
       FROM events e
   ) ranked
   WHERE rn <= 3;
   ```

   Уникальный `id` разрешает совпадения времени. Если нужны все строки, разделяющие призовое место, выбирают `RANK`/`DENSE_RANK` и отдельно определяют правило. Порядок вывода задают внешним ORDER BY.

6. Когда использовать `EXISTS`, `IN` и JOIN для проверки наличия связанной записи? Чем различаются `NOT EXISTS` и `NOT IN`, если встречается NULL?

   **Ответ:** `EXISTS` проверяет наличие строки и не размножает внешние строки; `IN` проверяет принадлежность набору; JOIN нужен также для получения столбцов связанной таблицы, но может породить несколько строк на один объект. Планировщик способен преобразовывать эти формы, поэтому скорость проверяют по плану.

   В `NOT IN` наличие NULL в наборе может сделать результат UNKNOWN для несовпавших значений и исключить их из WHERE. Для поиска отсутствующей связи часто яснее коррелированный `NOT EXISTS`. Сравнения с NULL внутри его подзапроса всё равно подчиняются обычной SQL-семантике.

7. Что такое CTE и рекурсивный CTE? Как написать обход иерархии и защититься от циклов в данных?

   **Ответ:** CTE именует подзапрос через WITH, улучшая структуру запроса; это не обязательная временная таблица. Рекурсивный CTE объединяет начальные строки и шаг, использующий предыдущий результат.

   ```sql
   WITH RECURSIVE tree AS (
       SELECT id, parent_id, ARRAY[id] AS path
       FROM nodes WHERE id = 1
       UNION ALL
       SELECT n.id, n.parent_id, t.path || n.id
       FROM nodes n JOIN tree t ON n.parent_id = t.id
       WHERE NOT n.id = ANY(t.path)
   )
   SELECT * FROM tree;
   ```

   Здесь путь предотвращает повторное посещение узла внутри ветви. В PostgreSQL есть также `CYCLE`; глубину и объём результата ограничивают по задаче. [CTE](https://www.postgresql.org/docs/current/queries-with.html).

8. Как реализовать optimistic locking через поле версии? Чем конфликт версии отличается от ошибки сериализации и когда нужно повторять всю транзакцию?

   **Ответ:** Клиент читает версию и обновляет строку только при её совпадении:

   ```sql
   UPDATE documents
   SET body = $1, version = version + 1
   WHERE id = $2 AND version = $3;
   ```

   Ноль изменённых строк означает отсутствие объекта либо конфликт версии. Приложение перечитывает данные и решает, допустимо ли повторить изменение; нельзя молча затереть чужую правку.

   Ошибка сериализации означает, что БД не смогла обеспечить выбранную изоляцию. Обычно повторяют всю транзакцию с новым снимком и ограничением попыток, а не только последний UPDATE. Внешние побочные эффекты требуют отдельной защиты от повторов.


## 9. PostgreSQL: индексы, эксплуатация и восстановление — P1/P2

Сейчас: есть MVCC, VACUUM, ANALYZE, блокировки, составные и частичные индексы, EXPLAIN и режимы репликации. Типы индексов и восстановление данных раскрыты недостаточно. Вопросы 1–4 — P1, 5–8 — P2.

1. Как устроен B-tree индекс и какие операции он ускоряет? Для каких запросов вместо него подходят GIN, GiST или BRIN?

   **Ответ:** B-tree — сбалансированная структура упорядоченных ключей: подходит равенству, диапазонам и сортировке при подходящем порядке индекса. GIN индексирует компоненты составных значений, например элементы массивов или лексемы. GiST — расширяемая структура для пространственных и других специализированных операторов. BRIN хранит сводки диапазонов страниц и полезен на больших таблицах с корреляцией значений и физического порядка.

   Тип выбирают по операторам и нагрузке: специализированный индекс не является универсально более быстрым. [Типы индексов](https://www.postgresql.org/docs/current/indexes-types.html).

2. Чем Index Scan, Bitmap Heap Scan и Index Only Scan отличаются по работе с таблицей? Как `INCLUDE` и visibility map влияют на возможность избежать чтения heap?

   **Ответ:** Index Scan находит указатели в индексе и обращается к строкам heap. Bitmap Heap Scan сначала собирает bitmap подходящих адресов, затем читает страницы таблицы более сгруппированно. Index Only Scan может взять все необходимые значения из индекса.

   `INCLUDE` добавляет полезные столбцы без включения их в ключ поиска. Но для проверки MVCC-видимости чтение heap всё ещё нужно, если visibility map не отмечает страницу как all-visible. Поэтому название Index Only Scan не гарантирует нулевое число heap fetches. [Index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html).

3. Когда нужен индекс по выражению? Почему условие с функцией или приведением типа может не использовать ожидаемый индекс?

   **Ответ:** Индекс по выражению хранит результат вычисления, например `CREATE INDEX ON users (lower(email))`, и подходит запросам с согласованным выражением. PostgreSQL требует immutable-функции в индексируемом выражении.

   Обычный индекс по `email` не обязательно поможет условию `lower(email) = ...`; аналогично приведение типа может изменить применимый оператор. Иногда лучше преобразовать параметр, а не столбец. Совпадение выражения ещё не заставляет планировщик выбрать индекс: учитываются селективность, статистика и цена доступа.

4. Как применять `pg_stat_activity`, `pg_stat_statements` и сведения об ожиданиях, чтобы отличить медленный запрос от ожидания блокировки или перегрузки БД?

   **Ответ:** `pg_stat_activity` показывает текущие сессии, запросы, состояние и `wait_event_type`/`wait_event`; `pg_blocking_pids(pid)` помогает найти блокирующую сессию. `pg_stat_statements`, если расширение настроено, агрегирует статистику запросов: вызовы, суммарное и среднее время, обработанные строки и I/O.

   Сначала определяют: запрос выполняется, ждёт lock, I/O или простаивает в транзакции. Затем сопоставляют с CPU, диском, числом соединений и планом. Высокое время запроса не доказывает нехватку CPU, а `EXPLAIN ANALYZE` действительно выполняет запрос.

5. Что такое WAL, checkpoint и crash recovery? Чем журнал предзаписи отличается от резервной копии?

   **Ответ:** WAL фиксирует изменения до записи соответствующих страниц данных на устойчивый носитель. Это позволяет после сбоя восстановить согласованное состояние через воспроизведение необходимых записей. Checkpoint сохраняет необходимые грязные страницы и контрольную точку, сокращая объём последующего recovery.

   WAL сам по себе не заменяет backup: для восстановления нужен исходный набор данных и достаточная непрерывная история журнала. Успешный COMMIT и гарантии сохранности зависят также от настроек durability и надёжности хранилища.

6. Чем логический backup отличается от физического и как работает point-in-time recovery? Как проверить восстановление после случайного удаления данных?

   **Ответ:** Логический backup содержит определения объектов и данные для восстановления через SQL/формат dump. Физический сохраняет файлы кластера и используется совместно с WAL. Для PITR восстанавливают подходящую базовую копию и проигрывают непрерывный архив WAL до выбранного момента или позиции.

   После случайного DELETE восстанавливают отдельное окружение до ошибки, проверяют данные и выбирают способ возврата с учётом более поздних корректных записей. Регулярная учебная реставрация проверяет не только наличие файлов, но и достижимые RPO/RTO. [PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).

7. Чем физическая репликация отличается от логической? Как replication lag влияет на чтение после записи, а replication slots — на удержание WAL?

   **Ответ:** Физическая репликация передаёт WAL для воспроизведения изменений кластера на уровне хранения. Логическая передаёт изменения опубликованных таблиц в терминах данных; она позволяет избирательность, но требует управления совместимостью схем и не переносит автоматически все объекты, например DDL.

   При отставании реплики чтение после записи может вернуть старые данные: критическое чтение направляют на primary либо ждут применения нужной позиции. Replication slot удерживает необходимые записи WAL; забытый или медленный потребитель способен заполнить диск, поэтому контролируют lag и удерживаемый объём.

8. Для чего нужен PgBouncer? Чем session pooling отличается от transaction pooling и какие ограничения это накладывает на состояние сессии приложения?

   **Ответ:** PgBouncer уменьшает число серверных соединений, обслуживая много клиентских. Session pooling закрепляет соединение до отключения клиента; transaction pooling выдаёт его на транзакцию и затем возвращает в пул.

   При transaction pooling нельзя рассчитывать на обычный session-level SET, временные объекты между транзакциями, LISTEN или session advisory locks. Используют транзакционно-локальные настройки и проверяют возможности конкретной версии. Поддержка protocol-level prepared statements зависит от конфигурации `max_prepared_statements`; SQL-команда PREPARE — отдельный случай. [Совместимость PgBouncer](https://www.pgbouncer.org/features.html).


## 10. Базы данных из Go: соединения и транзакции — P1

Сейчас: в `golang/backend` есть закрытие `rows` и outbox. Управление пулом, выполнение запросов и транзакционный код отдельно не разобраны.

1. Что представляет собой `sql.DB` и чем он отличается от `sql.Conn` и `sql.Tx`? Почему пул обычно создают на время жизни приложения?

   **Ответ:** `sql.DB` — безопасный для конкурентного использования handle с пулом соединений. `sql.Conn` резервирует одно соединение до `Close`, а `sql.Tx` выполняет транзакцию на выделенном соединении до Commit/Rollback.

   Один пул создают для каждой необходимой конфигурации подключения и переиспользуют. Создание `sql.DB` на каждый HTTP-запрос лишает приложение общего контроля соединений и увеличивает накладные расходы. `db.Close()` обычно вызывают при завершении приложения.

2. Что делают `sql.Open` и `PingContext`? Как проверять доступность БД при запуске и обрабатывать её временную недоступность?

   **Ответ:** `sql.Open` создаёт handle и может проверить аргументы, но обычно не устанавливает реальное соединение. `PingContext` проверяет возможность связи с БД в пределах контекста.

   При запуске задают короткий дедлайн и явную политику: завершиться с ошибкой либо ждать с ограниченными повторами. При временном сбое не пересоздают пул на каждый запрос; ограничивают время ожидания и обрабатывают ошибку. Успешный Ping подтверждает доступность в момент проверки, но не корректность схемы и всех будущих операций.

3. Как выбрать `MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime` и `ConnMaxIdleTime`? Как учитывать суммарное число соединений всех реплик сервиса?

   **Ответ:** `MaxOpenConns` ограничивает общее число открытых соединений; при достижении лимита запросы ждут свободное. `MaxIdleConns` задаёт число сохраняемых свободных соединений. `ConnMaxLifetime` ограничивает их возраст, `ConnMaxIdleTime` — время простоя.

   Бюджет считают по максимуму реплик, включая временные реплики раскатки, другие сервисы и резерв администрирования. Через `DB.Stats()` следят за `InUse`, `Idle`, `WaitCount`, `WaitDuration`. Слишком большой пул способен ухудшить работу БД, а слишком маленький — увеличить очередь в приложении.

4. Чем `ExecContext`, `QueryContext` и `QueryRowContext` отличаются по назначению? На каком этапе появляется `sql.ErrNoRows`?

   **Ответ:** `ExecContext` выполняет команду без набора строк и возвращает `Result`. `QueryContext` возвращает `Rows`: нужны закрытие и проверка `rows.Err()` после обхода. `QueryRowContext` предназначен для одной строки; ошибка, включая `sql.ErrNoRows`, проявляется при `Scan`.

   ```go
   var name string
   err := db.QueryRowContext(ctx,
       "SELECT name FROM users WHERE id = $1", id).Scan(&name)
   if errors.Is(err, sql.ErrNoRows) { /* сущность не найдена */ }
   ```

   Несколько строк не дают ошибку QueryRow: используется первая, поэтому уникальность результата обеспечивают запросом или схемой.

5. Как корректно использовать `BeginTx`, `Commit` и `Rollback` на всех путях выхода? Почему вызов через `db` вместо `tx` нарушает границы транзакции?

   **Ответ:** После `BeginTx` все операции транзакции выполняют через `tx`, на каждом шаге проверяя ошибку. Отложенный Rollback покрывает ранние выходы; после успешного Commit он не отменит уже зафиксированное.

   ```go
   func setName(ctx context.Context, db *sql.DB, id int64, name string) error {
       tx, err := db.BeginTx(ctx, nil)
       if err != nil { return err }
       defer tx.Rollback()

       _, err = tx.ExecContext(ctx,
           "UPDATE users SET name = $1 WHERE id = $2", name, id)
       if err != nil { return err }
       return tx.Commit()
   }
   ```

   Вызов через `db` может уйти на другое соединение, вне транзакции, и даже зависнуть при исчерпании пула. Ошибку Commit нельзя игнорировать. [Транзакции в Go](https://go.dev/doc/database/execute-transactions).

6. Как сканировать SQL NULL в Go и когда нужны `sql.Scanner` и `driver.Valuer` для собственного типа?

   **Ответ:** SQL NULL представляют явно: через `sql.NullString`, `sql.NullInt64`, обобщённый `sql.Null[T]` в поддерживающих его версиях либо nullable-указатель. У Null-типов поле `Valid` различает отсутствие и нулевое значение.

   Собственный `Scanner.Scan` преобразует значение драйвера в тип приложения; `driver.Valuer.Value` выполняет обратное преобразование в допустимый тип драйвера или nil. Например, так задают доменный тип денег/статуса. Данные `[]byte`, полученные от драйвера в Scan, копируют, если сохраняют после вызова.

7. Как отмена context влияет на запрос и транзакцию? Что делать, если соединение потеряно во время `Commit` и результат операции неизвестен?

   **Ответ:** Контекст ограничивает ожидание соединения и передаётся драйверу для отмены операции. Фактическое прерывание зависит от поддержки драйвера. Отмена контекста, с которым начат `BeginTx`, приводит к откату со стороны `database/sql`; Commit не может считаться успешным без успешного результата.

   Если соединение потеряно во время Commit, сервер мог уже зафиксировать данные. По одной сетевой ошибке нельзя заключить, что записи нет. Результат сверяют по устойчивому ID операции; повтор выполняют с защитой от дублирования, а не безусловным повторным списанием.

8. Как выявить N+1-запросы и уменьшить число обращений к БД? Когда применять batch, подготовленные запросы и bulk-вставку?

   **Ответ:** N+1 возникает, когда после одного запроса списка выполняют отдельный запрос для каждого элемента. Его замечают по tracing, счётчику SQL-вызовов на запрос и повторяющимся шаблонам запросов.

   Данные загружают JOIN либо несколькими групповыми запросами с последующим связыванием в памяти. Batch снижает число сетевых обменов, prepared statement помогает повторному выполнению одной формы SQL, bulk-вставка/COPY — массовой загрузке. Prepared statement сам по себе N+1 не устраняет. Размер пакета ограничивают памятью, параметрами драйвера и длительностью транзакции.
